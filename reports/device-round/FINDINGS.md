# 第五轮：用户设备上实际大众对局的日志分析

当前结果：这份 ZIP 成功提供了真实对局日志，但未找到可直接显示其他三家实时暗牌的数据。已经检查的额外摸牌字段均为空值；不能用这份日志制作已验证有效的透视功能。结论限定于本次记录到的字段和一局样本，不代表证明服务端从不下发任何额外数据。

## 导出与对局范围

- 用户设备系统 17.0，欢乐麻将版本 8.19.112，与最初提供的安装包一致。
- 工具读到了一个目标应用容器；扫描 1,964 个条目，列出 16 个候选文件，用户选择导出 5 个文件。清单未记录扫描错误、截断或跳过文件。
- 主日志为约 4.4 MB 的明文文本，包含 32,375 行。
- 对局日志明确使用 ModuleTuidaohu49。记录到一局发牌，日志当地时间为 22:56:01；胡牌与 FINISH_V2 结算通知为 22:58:45。
- 共匹配 79 条传统消息分发记录，包括发牌、出牌、碰杠处理、胡牌和结算。这是实际执行传统流程的证据；NewGame 一词在其他日志中的出现不能单独证明该局使用新引擎。

原始 ZIP 未推入 Git 历史。远程分析输入以 AES-256 加密附件保存，解密口令放在 Actions secret；公开产物只包含白名单统计、时间和协议字段事实，不包含账号、令牌、完整消息体和真实手牌值。

## 实际检查到的牌值字段

| 检查项 | 本次观察 |
| --- | --- |
| 自己的初始牌 | 一条记录，13 张，均不是静态定义的牌背占位值 |
| 自己的摸牌日志 | 15 条已解析记录，均有正的单张牌值；不公开具体牌值 |
| 等待消息 | 52 条 JSON 记录全部解析，未漏掉任何匹配到的 HandleWait 标记 |
| 其中带有正摸牌数量的等待消息 | 40 条；不能把全部 52 条都称为实际摸牌 |
| chExCmd | 52 条全部为 0 |
| nExtraTilesNum | 52 条全部为 0 |
| ExtraTiles | 52 条全部为空数组 |
| 传统完整手牌 TLV 名称 | 已记录的 live 阶段 Handle TLV 类型中，EM_UP_TLV_HAND_TILES 与 EM_DN_TLV_KEY_HAND_TILES 均未出现 |
| 其他玩家手牌模型快照 | 没有解析到，不能声称本次直接读到了另外三家的完整内存模型 |

MJDef 的静态定义中 MJ_BACK=0，是在 GitHub 上从恢复出的 Hall 程序集重新提取的。日志中自己的初始牌有真实值，说明本次不是只有完全不可读的加密内容；但自己的牌不能当作对手暗牌证据。

TLV 日志在处理循环中可能重复记录同一个类型，因此统计中的类型出现次数不是独立网络包数量。未出现某个已记录类型，不等于排除了所有未写入日志的其他消息内容。

## 仍未验证的负载

这局同时记录到了压缩 protobuf 类型和牌墙能力相关类型。源码中 EM_UP_TLV_PROTO_BUF 会先解压并解析 UnitProtoValue，其中一条处理路径用于服务端听牌/推荐信息。牌墙能力类型也能表示按位置显示的特定牌信息；其名称本身不等于完整隐藏牌墙或三家手牌。

本轮统计没有取得这些消息的完整原始负载，不能把它们解释为已经掌握对手暗牌，也不能仅凭额外摸牌字段为零就宣称所有其他负载都没有数据。要继续验证这些路径，需要采集相应消息的实际负载，而不是再把默认空数组当成牌值。
