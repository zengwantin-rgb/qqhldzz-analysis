# 传统对局消息观察器 0.2.2 Beta

本版在已验证可用的游戏运行时中，尝试加载本项目自己的托管观察器，订阅传统和 protobuf 两条对局消息通道。只支持当前已核对的游戏 build 8.19.112。

## 操作

1. 下载 MJMessageObserver.dylib 到“文件”App。
2. 从多任务界面完全关闭欢乐麻将。
3. 在 TrollFools 中选择 com.tencent.happymj 的欢乐麻将，移除旧的 MJMessageObserver.dylib（以及仍存在的 MJRuntimeProbe.dylib），再导入本版 MJMessageObserver.dylib。
4. 打开游戏，在大厅等待约 20 秒。看到“诊断：已就绪，可以进入对局”后，再进入大众麻将打一局。
5. 游戏内出现“已记录 ≥N 条消息”表示至少有相应数量的解码事件已写入本地文件；它不表示已经取得对手暗牌。
6. 完全关闭游戏，用已有的 1.2 工具执行“扫描 → 完整选择 → 导出”，提供新 ZIP。

如果提示“启动未完成”“记录待检查”，或一直没有提示，先导出状态日志，不用继续重复打牌。若游戏无法启动，在 TrollFools 中移除此库后重开；不要卸载游戏。

## 保存内容与范围

本地文件在 Documents/MJMessageObserver/：observer-status.log 保存加载和注册状态，每次启动创建独立的 game-events-*.log 保存对局事件。

记录通常是游戏已解码对象经原有 TDR / protobuf 序列化器重新编码的结果。TDR 序列化失败时，改为保存有大小和遍历上限的公共协议字段 JSON，格式单独标记；只读取当前消息与 TLV 的有效分支，省略空字段，不把其他分支当成本条消息；字段备份也失败时仅跳过该消息，继续后续消息。日志只保留固定错误阶段、类别和消息编号，不保存异常文本。以上两种格式都不是原始网络字节。与原处理器的执行先后关系还未验证。每次启动最多 512 条、18 MiB，每条最多 256 KiB；超过上限停止写入本轮采集，不改变正常对局流程。

事件文件可能包含本局完整消息字段，包括牌数据和玩家标识。它只保存在本机，不会自动上传；沿用当前私密 ZIP 导出流程，公开仓库仅保留经过筛选的统计结果。

本库不替换收包函数，不发送或修改对局请求，不调整牌、规则或游戏设置。状态条不接收触摸。测试完先关闭游戏，再通过 TrollFools 移除此库，即可停止后续启动时的观察。

## 验证

已通过日志边界和编码测试、原版本元数据引用编译、隔离文件创建测试、ARM64 编译、ad-hoc 签名及系统依赖检查。此前 0.1 探针已在用户设备上证实所需核心 API 和事件类型可见。

用户导出的 0.2.0 真机日志已确认：托管加载、订阅及第一条消息保存成功；随后出现处理异常，旧版停止了后续采集。0.2.1 真机日志进一步确认：新采集保存了 57 条有效消息，但发牌（1）与全桌状态（8）的字段备份仍失败。0.2.2 根据原版协议的 96 个消息、203 个 TLV 选择器，只遍历当前分支并省略空字段。相同字段读取逻辑已在隔离环境成功解码这份 ZIP 的全部 58 条记录（包括此前保留的 1 条）；发牌与全桌状态的手机采集效果仍待验证。实时对手手牌显示尚未实现，不能承诺服务端会提供所需牌值。
